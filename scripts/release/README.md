# authtempo-release

The release checks of plan 12j. Never published: the name has no scope, and `private` is true.

Each check is a `.ts` file that Node runs by type stripping. Each check has a pure function and a vitest test over the fixtures in `test/fixtures/`. Its entry reads the repository and prints one summary line:

```
<name>: PASS|FAIL <key>=<n> ... failures=<n>
```

A check that reads zero items fails. Read the failure count from the summary line, not from the exit code alone.

## The checks

- `src/check-packages.ts`: each workspace package has its own name and is in exactly one list. The released list is `fixed[0]` of `.changeset/config.json`, the one fixed group, and `linked` is empty. The unreleased list is `release/unreleased.json`, with one reason for each package, and the same names are in `ignore` of `.changeset/config.json`. Each released package is private on `main` and has the group version. The group version is never `0.0.x` above `0.0.0`, because the first release is `FIRST_RELEASE` (0.1.0). So a version pull request with only patch changesets fails before the merge. Each reference to a workspace package, scoped or not, and each `@authtempo` reference is `workspace:*`. A released package names no unreleased package in `dependencies`, `peerDependencies`, or `optionalDependencies`.
- `src/check-changesets.ts`: each change to a released package since the merge base with `main` has a changeset that names the package. The rules are in `.changeset/README.md`. Only a changeset that is new since the merge base counts. A changeset on `main` covers nothing on the branch, also when the branch changes it. `changeset status` runs beside it as a note, and its exit code never decides.
- `src/check-records.ts`: each changelog, the advisory record, and each shipped migration at the merge base with `main` stays the same. Each one is in the working tree with the same bytes. A changelog grows at the top, and the advisory record grows at the end. `RECORD_GLOBS` holds the rule of each file. No check holds the spec, the plan index, the plan files, or the ledgers: a review holds them.
- `src/check-support.ts`: `release/support.json` keeps owner decision 3 (spec 33 item 7). At most one minor is current. A minor with security fixes has a newer minor, and its last day is 3 months after the release of that minor, at most 7 days later. A minor past that day is unsupported. From each schema version of a supported minor, each `packages/adapter-*` has a migration file for each version up to `SCHEMA_VERSION`. An empty folder of its own fails. An adapter with no `migrations` or `src/migrations` folder needs an entry in `release/migration-sources.json` with `from`, `reason`, and `proof`. The check then reads the files of the `from` folder. The entry fails when that folder has no migration, when the `proof` is not a file under `packages/<adapter>/test/`, and when the adapter has a folder of its own or no package. A `__proto__` key is an entry with no package, so it fails. An empty table passes with the note `no release exists`. The site check `check-security-policy` holds the table of `SECURITY.md` to the same file.
- `src/check-pack.ts <tarball>...`: each release tarball holds only `files` and the always-shipped files (`package.json`, `README.md`, `LICENSE`). It holds no forbidden name, and no binary file that its package does not declare. It holds each `exports`, `main`, `types`, and `bin` target, and each needed file of `release/pack-needs.json`. A need that ends in `/` is a folder with at least one file. Each released package has exactly one tarball. A tarball entry that is not a regular file or a folder fails, such as a link. A path with a `..` part fails too. The manifest has the group version, `license` MIT, the repository url and folder, `publishConfig` with public access and provenance, no `private`, and no `workspace:` text. The version is never `0.0.0`, which the scaffold reads as unpublished. It is never `0.0.x` above `0.0.0` either, because the first release is `FIRST_RELEASE` (0.1.0). The packed manifest and the workspace manifest hold no script that npm or pnpm runs at pack or publish: `prepack`, `postpack`, `prepare`, `prepublish`, `prepublishOnly`, `publish`, or `postpublish`. The tarball has a `CHANGELOG.md` and a `LICENSE` with the bytes of the root `LICENSE`. Core's `authtempo.breaking` and `authtempo.deprecations` equal its changelog and `release/deprecations.json`. A source that it cannot read, such as a missing or bad `release/deprecations.json`, gives a FAIL summary line. The dry run of Task 6 runs it in a release copy.
- `src/check-deprecations.ts [version]`: each item of `release/deprecations.json` keeps its markers. A marker is a file and a text that exist only while the item stays. Below `removeIn` each marker is in the tree, and at or above it each marker is gone. At `0.0.0`, before the first release, every item is live. `removeIn` is the minor after `since`, `since` is never `0.0.0`, and `docs` is the anchor of the id on `/docs/reference/deprecations/`. The words "for one release" in the shipped text, also over a line break, lie inside a marker text of their file. The shipped text of each released package is its `README.md`, each file under `src/`, and each file of its `files` field but `dist`. A glob in `files` fails. The version is the group version when you give none. `check-pack` and `prepare` read the same register through `src/lib/deprecations.ts`, and the file is required.
- `src/check-workflows.ts`: the two workflows under `.github/workflows/` keep the rules of spec 33 item 5. Each action is pinned to a 40-character commit SHA with a `# v<major>.<minor>.<patch>` comment. `ci.yml` runs on a pull request and a push to `main` with `contents: read`. `release.yml` runs on a push of a tag `v*` with top-level `permissions: {}`. Only its job `publish` has `id-token: write`, in the environment `release`. Each runner is an `ubuntu-<version>` runner of GitHub. No `run:` line holds an expression, no line names a token, and no step but `publish.ts` publishes. Each level holds only the keys that its rule names. `TOP_KEYS` holds the top, `JOBS` holds each job and step, and `WITH_KEYS` holds each `with` block. Any other key fails, such as `if`, `continue-on-error`, `env`, or `repository`. Each job has its steps in the order of `JOBS`, and each Node is at or above `NODE_FLOOR`. Each `node <path>` of a run line is a file of the tree. Each `pnpm <script>` is a root script, and each `node <path>` of that script exists. `LATER` lists the files that a later task adds, with the task and the plan line. The check skips them, and an entry whose file exists fails as stale. The check reads a YAML subset of its own and refuses any other form. A third workflow fails.
- `src/check-tag.ts <tag>`: the release tag is `v<version>` with no prerelease part, and it equals the group version. It is never `v0.0.x`, because the first release is `FIRST_RELEASE` (0.1.0). Its commit is on `origin/main`, or on `origin/release/<major>.<minor>` for a patch. The job `check` of `release.yml` runs it first.
- `src/publish.ts <folder>`: runs only in the job `publish` of `release.yml`. It checks the npm version against `NPM_FLOOR` and each tarball against `SHA256SUMS`. Then it publishes each version that the registry lacks, with `npm publish --access public`. Each package publishes after each package of its `dependencies`, `peerDependencies`, and `optionalDependencies`, so core goes first. The newest version gets the dist-tag `latest`, and an older minor gets `release-<major>.<minor>`. It stops at the first publish that fails. It prints one line for each version: published, not published, or skipped. So after a half release, the output names each version that npm has and each one that it lacks. It imports only Node modules and `src/lib/release-facts.ts`, because the job runs no install. Its tests replace each child process, so no test publishes.
- `src/prepare.ts`: it runs only in a release copy, a folder with the `.release-copy` file and no `.git`. For each released package, it removes `private`. It writes `license` from the root `package.json`, `repository` from `release/repository.json` with the package folder, and `publishConfig` with public access and provenance, after `version`. It copies the root `LICENSE` into the package folder. Core also gets `authtempo.breaking` from its `CHANGELOG.md` and `authtempo.deprecations` from `release/deprecations.json`. A released package with no `engines` fails.
- `src/dry-run.ts` (`pnpm release:dry-run [--keep]`): it stops with exit 2 on a dirty checkout. It copies `git archive HEAD` into a new temp folder and writes the `.release-copy` file. Then it installs offline and writes one minor changeset for the group. It runs `changeset version`, `prepare`, and the build of the released packages with the cache off. The site build fails on a changelog version with no release date, and the site ships in no tarball. The commands of the release copy are one list, `src/lib/release-copy.ts`, which the job `check` of `release.yml` also runs. `check-workflows` holds each run line of the job to the list. It packs each released package with `--ignore-scripts`, runs `check-pack` on the tarballs, `npm publish <tarball> --dry-run` for each, and `pnpm publish -r --dry-run --ignore-scripts`. The pnpm list must equal the tarball list. Last, it installs the tarballs offline in a copy of `release/smoke/` and runs `smoke.mjs`. It stops at the first step that fails. It prints one line per tarball (`<name>@<version> <sha256> files=<n>`) and the summary line `release-dry-run: PASS packages=<n> of <n> version=<v> tarballs=<n> files=<f> smoke=<k> failures=0`. Each publish call has `--dry-run` and the registry `http://127.0.0.1:9`, where nothing listens, also as the `@authtempo` scope registry. Each child gets `PATH`, `HOME`, `TMPDIR`, and `LANG` from your env, and no other key of it. `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_GLOBALCONFIG` name two empty files in the temp folder, so no npmrc and no token reaches a child. The run fails when an npm or pnpm line names another registry. It never commits, tags, or pushes. It deletes the temp folder unless you give `--keep`.
- `src/check-dependencies.ts`: each direct dependency of each workspace package and of the root package has one row in `release/dependencies.json` for each kind: `runtime`, `peer`, or `dev`. Each row lists the versions and the users that the manifests hold, a reason, and a read date. A runtime row also names its seam. The runtime closure of the released packages comes from `pnpm-lock.yaml` and the license of each installed package. It holds only MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, and 0BSD, or a package of `release/license-exempt.json`.
- The check also reads `pnpm-workspace.yaml`. `minimumReleaseAge` stays at 1440 or more. Each `minimumReleaseAgeExclude` entry names a row, as `<name>` or `<name>@<version>`, so a pattern such as `*` fails. Each `allowBuilds` entry has its own reason comment, in block form or in flow form. `dangerouslyAllowAllBuilds`, `overrides`, `packageExtensions`, `patchedDependencies`, `catalog`, and `catalogs` fail while present: no rule reads them yet. The keys `pnpm` and `resolutions` of the root `package.json` also fail while present, for the same reason.
- `src/check-osv.ts`: sends the name and version of each package of that closure to the OSV batch query. It fails on an advisory with no live exemption in `release/osv-exempt.json`, and when OSV gives no answer. When `OSV_URL` names another server, the check prints a note under the summary line. Only the owner writes an exemption.

The forbidden names are one list, `FORBIDDEN_PACK_NAMES` in `src/lib/pack-rules.ts`. Each older `proof/pack-files.mjs` imports it through `forbiddenMatch`, so a new name reaches every proof.

Each git test makes its own repository in the temp folder (`TMPDIR`) and never reads the history of this repository.

Run a check from the repository root. The `ref` is `main` when you give none:

```sh
node scripts/release/src/check-packages.ts
node scripts/release/src/check-changesets.ts [ref]
node scripts/release/src/check-records.ts [ref]
node scripts/release/src/check-support.ts
node scripts/release/src/check-workflows.ts
node scripts/release/src/check-deprecations.ts [version]
```

Run the tests with the cache off:

```sh
pnpm turbo run test typecheck --filter=authtempo-release --force
```

## A new workspace package

Put the package in exactly one list. To release it, add its name to `fixed[0]` of `.changeset/config.json`. To keep it unreleased, add its name to `ignore` of `.changeset/config.json` and to `release/unreleased.json` with one reason. `check-packages` fails until the package is in one list. A released package also needs its entry in `release/pack-needs.json`: the check-pack test fails until it exists.

## A new dependency

Add one row to `release/dependencies.json` for each new name and kind, or add the new user and version to the row that exists. Read the version, the license, and the install script with `npm view <name>@<version> license scripts time --json`. Write the date of the read in `read`, in the form YYYY-MM-DD. A runtime row names the file that holds each import in `seam`. `check-dependencies` fails until the row matches the manifests.

A package of the runtime closure with an `os`, a `cpu`, or a `libc` field in `pnpm-lock.yaml` is a platform package. pnpm skips it on a machine of another platform, so the check cannot read its package.json there. Give it a `platform` row with `name`, `versions`, `license`, `reason`, and `read`, and no users. Name the source of the license in the reason. The check fails on a skipped platform package with no row. It also fails on a row that disagrees with an installed package.json, or that matches no platform package of the closure.

## The exemption files

`release/license-exempt.json` lists each package of the runtime closure that has a license outside the allow list. Each entry has `name`, `version`, `license`, `reason`, and `read` (YYYY-MM-DD). An entry matches one name, one version, and one license exactly. An entry that matches no package of the closure fails.

`release/osv-exempt.json` lists each open advisory that the owner accepts. Each entry has these fields:

- `id`: the OSV id of the advisory.
- `name` and `version`: the package of the closure.
- `reason`: why the advisory does not apply.
- `read`: the date that the owner read the advisory (YYYY-MM-DD), on or before the day of the run.
- `expires`: the last day of the exemption (YYYY-MM-DD), on or after `read`, and at most 90 days after it.

An entry that has expired, or that matches no package of the closure, fails.
