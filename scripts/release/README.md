# authtempo-release

The release checks of plan 12j. Never published: the name has no scope, and `private` is true.

Each check is a `.ts` file that Node runs by type stripping. Each check has a pure function and a vitest test over the fixtures in `test/fixtures/`. Its entry reads the repository and prints one summary line:

```
<name>: PASS|FAIL <key>=<n> ... failures=<n>
```

A check that reads zero items fails. Read the failure count from the summary line, not from the exit code alone.

## The checks

- `src/check-packages.ts`: each workspace package has its own name and is in exactly one list. The released list is `fixed[0]` of `.changeset/config.json`, the one fixed group, and `linked` is empty. The unreleased list is `release/unreleased.json`, with one reason for each package, and the same names are in `ignore` of `.changeset/config.json`. Each released package is private on `main` and has the group version. The group version is never `0.0.x` above `0.0.0`, because the first release is `FIRST_RELEASE` (0.1.0). So a version pull request with only patch changesets fails before the merge. Each reference to a workspace package, scoped or not, and each `@authtempo` reference is `workspace:*`. A released package names no unreleased package in `dependencies`, `peerDependencies`, or `optionalDependencies`.
- `src/check-changesets.ts`: each change to a released package since the merge base with `main` has a changeset that names the package. The rules are in `.changeset/README.md`. Only a changeset that is new since the merge base counts. A changeset on `main` covers nothing on the branch, also when the branch changes it. A file that `rewrite-unpublished` writes needs no changeset on the version branch, where the group version differs from the merge base. That branch rewrites its pre-release text with no code change, and `check-pack` holds the result. `changeset status` runs beside it as a note, and its exit code never decides. A change to a root input of `ROOT_INPUTS` (`src/lib/root-inputs.ts`) counts as a change of each package of its row. Examples are `tsconfig.base.json` of each build and `release/deprecations.json` of core. A test holds the list to the build scripts, to `prepare`, to the stacks of the CLI, and to `release/migration-sources.json`. A changeset with a `Breaking:` line names each package as a `minor`, or as a `major` from `1.0.0`. `breakingByMinor` of `src/check-pack.ts` reads each `Breaking:` line of a change, also a later line, which Changesets writes with two spaces in front.
- `src/check-records.ts`: each changelog, the advisory record, and each shipped migration at the merge base with `main` stays the same. Each one is in the working tree with the same bytes. A changelog grows at the top, and the advisory record grows at the end. `RECORD_GLOBS` holds the rule of each file. No check holds the spec, the plan index, the plan files, or the ledgers: a review holds them.
- A push to `main` and a tag of a `main` commit have a merge base equal to `HEAD`. A compare with `HEAD` reads no change, so `check-records` then compares with the newest release tag before `HEAD`. With no tag, it compares with `RECORDS_BASE` of `src/lib/release-facts.ts`, and a note names the base. A change that is not committed yet is held against `HEAD` too. It never prints PASS with no compare: a `RECORDS_BASE` that is `HEAD` or not an ancestor of `HEAD` fails.
- `src/check-support.ts`: `release/support.json` keeps owner decision 3 (spec 33 item 7). At most one minor is current. A minor with security fixes has a newer minor. Its last day is 3 months after the release of that minor, at most 7 days later. A minor past that day is unsupported. From each schema version of a supported minor, each `packages/adapter-*` has a migration file for each version up to `SCHEMA_VERSION`. An empty folder of its own fails. An adapter with no `migrations` or `src/migrations` folder needs an entry in `release/migration-sources.json` with `from`, `reason`, and `proof`. The check then reads the files of the `from` folder. The entry fails when that folder has no migration, or when the `proof` is not a file under `packages/<adapter>/test/`. It also fails when the adapter has a folder of its own or no package. A `__proto__` key is an entry with no package, so it fails. At `0.0.0` an empty table passes with the note `no release exists`, and the line counts the adapters. Above `0.0.0` an empty table fails, because a release with no support row makes no promise. The minor of the group version needs its own row too, so a new minor with only older rows fails. The site check `check-security-policy` holds the table of `SECURITY.md` to the same file.
- `check-support` also reads the compat chains of `authtempo migrate --tables compat`, from `packages/compat-better-auth/migrations/`. Each folder there is a chain of `COMPAT_FOLDERS`: `d1`, `d1-before-1.7`, and `postgres`, the text of the Postgres runner. A folder with no row fails. A chain needs a step to each schema version, as an adapter does.
- `src/check-pack.ts <tarball>...`: each release tarball holds only `files` and the always-shipped files (`package.json`, `README.md`, `LICENSE`). It holds no forbidden name, and no binary file that its package does not declare. It holds each `exports`, `main`, `types`, and `bin` target, and each needed file of `release/pack-needs.json`. A need that ends in `/` is a folder with at least one file. Each released package has exactly one tarball. A tarball entry that is not a regular file or a folder fails, such as a link. A path with a `..` part fails too. The manifest has the group version, `license` MIT, the repository url and folder, `publishConfig` with public access and provenance, no `private`, and no `workspace:` text. The version is never `0.0.0`, which the scaffold reads as unpublished. It is never `0.0.x` above `0.0.0` either, because the first release is `FIRST_RELEASE` (0.1.0). Each version constant of `VERSION_CONSTANTS` in dist, such as `VERSION` of core, equals the version of the manifest. `changeset version` moves only `package.json`, so a literal in dist would ship `0.0.0`. The packed manifest and the workspace manifest hold no script that npm or pnpm runs at pack or publish. These are `prepack`, `postpack`, `prepare`, `prepublish`, `prepublishOnly`, `publish`, and `postpublish`. They hold no script that runs at each install of an app either: `preinstall`, `install`, or `postinstall`. The tarball has a `CHANGELOG.md` and a `LICENSE` with the bytes of the root `LICENSE`. Core's `authtempo.breaking` and `authtempo.deprecations` equal its changelog and `release/deprecations.json`. A source that it cannot read, such as a missing or bad `release/deprecations.json`, gives a FAIL summary line. It reads the text of each packed file for each form of the note in `UNPUBLISHED_FORMS` (`src/lib/unpublished.ts`), such as "not on a registry yet". It reads with no regard to case or to a line break. At `0.0.0`, each file of `UNPUBLISHED_FILES` holds the form of each of its notes, and no other packed file holds a form. Above `0.0.0`, no packed file holds one, so the version branch runs `rewrite-unpublished`. A file of `UNPUBLISHED_CODE` holds the note as code that shows it only at `0.0.0`, so it is exempt. Each entry of the two lists names a packed file, or it fails as stale. The summary line counts `marked`, the packed files with a form, and `listed`, the files of the list. A packed file with a path of a local machine fails, such as `/Users/<name>/`, `/home/<name>/`, or a Windows drive path (`LOCAL_PATH`). The dry run of Task 6 runs it in a release copy, and the check has no other rule for the dry run. It reads each tarball once. With `--sums <file>`, a PASS writes the SHA-256 of those bytes to the file in the form of `sha256sum`, and a FAIL writes no list.
- `src/check-deprecations.ts [version]`: each item of `release/deprecations.json` keeps its markers. A marker is a file and a text that exist only while the item stays. Below `removeIn` each marker is in the tree, and at or above it each marker is gone. At `0.0.0`, before the first release, every item is live. `removeIn` is the minor after `since`, `since` is never `0.0.0`, and `docs` is the anchor of the id on `/docs/reference/deprecations/`. The words "for one release" in the shipped text, also over a line break, lie inside a marker text of their file. The shipped text of each released package is its `README.md`, each file under `src/`, and each file of its `files` field but `dist`. A glob in `files` fails. The version is the group version when you give none. `check-pack` and `prepare` read the same register through `src/lib/deprecations.ts`, and the file is required.
- `src/check-workflows.ts`: the two workflows under `.github/workflows/` keep the rules of spec 33 item 5. Each action is pinned to a 40-character commit SHA with a `# v<major>.<minor>.<patch>` comment. `ci.yml` runs on a pull request and a push to `main` with `contents: read`. It runs `pnpm lint`, then the release check against the base branch of the pull request, or `main` on a push. `release.yml` runs on a push of a tag `v*` with top-level `permissions: {}`. Only its job `publish` has `id-token: write`, in the environment `release`. Each runner is an `ubuntu-<version>` runner of GitHub. No `run:` line holds an expression, no line names a token, and no step but `publish.ts` publishes. No `run:` line starts docker: `release-check` starts the test servers through `scripts/test-servers.mjs`. Each level holds only the keys that its rule names. `TOP_KEYS` holds the top, `JOBS` holds each job and step, and `WITH_KEYS` holds each `with` block. Any other key fails, such as `if`, `continue-on-error`, `env`, or `repository`. Each job has its steps in the order of `JOBS`, and each Node is at or above `NODE_FLOOR`. Each `node <path>` of a run line is a file of the tree. Each `pnpm <script>` is a root script, and each `node <path>` of that script exists. The check reads a YAML subset of its own and refuses any other form. A third workflow fails.
- `src/check-tag.ts <tag>`: the release tag is `v<version>` with no prerelease part, and it equals the group version. It is never `v0.0.x`, because the first release is `FIRST_RELEASE` (0.1.0). Its commit is on `origin/main`, or on `origin/release/<major>.<minor>` for a patch. The job `check` of `release.yml` runs it first.
- `src/publish.ts <folder>`: runs only in the job `publish` of `release.yml`. It checks the npm version against `NPM_FLOOR`. It checks each tarball against the SHA-256 list of the job output `sums` of the job `check`, which it reads from `RELEASE_SHA256SUMS`. The `SHA256SUMS` of the artifact must equal that list. A version that the registry holds must have the `dist.integrity` of its tarball, or nothing publishes. Then it publishes each version that the registry lacks, with `npm publish --access public`. Each package publishes after each package of its `dependencies`, `peerDependencies`, and `optionalDependencies`, so core goes first. The newest version gets the dist-tag `latest`, and an older minor gets `release-<major>.<minor>`. It stops at the first publish that fails. It prints one line for each version: published, not published, or skipped. So after a half release, the output names each version that npm has and each one that it lacks. It imports only Node modules and `src/lib/release-facts.ts`, because the job runs no install. Its tests replace each child process, so no test publishes.
- `src/verify-published.ts [version]`: the owner runs it after the end of the job `publish`, with the version of the tag. It is step 11 of "At each release" in `docs/release/RUNBOOK.md`. For each released name of `releasedNames`, it reads the version document of the group version from the public registry. Each document must hold `dist.attestations` with the SLSA provenance predicate. The check then reads the attestations of the version from the same registry. The provenance statement must name the package, the repository of `release/repository.json`, and `.github/workflows/release.yml`. Only a package version of `release/fallback-published.json`, keyed by `<name>@<version>`, may lack an attestation. The owner writes the entry after a publish by hand. An attestation with no provenance predicate fails at each version, and so does another predicate. The statement must also name the ref `refs/tags/v<version>`. No answer from the registry fails. Its test replaces the fetch, so no test reads npm.
- `src/rewrite-unpublished.ts`: the step of the first release in `docs/release/RUNBOOK.md`, after `changeset version`. It replaces each note of `UNPUBLISHED_FILES`, each note line of `PAGE_NOTES` on the pages of `UNPUBLISHED_PAGES`, and each text of `PRE_RELEASE_SENTENCES` with its published text. The published text puts the group version in the place of `<version>`, and an empty one removes the paragraph. It fails on a group at `0.0.0`, and on a text that its file lacks or holds twice. A note form left after the rewrite fails too. A run with a failure writes no file. Two texts have no published form: the support text of `SECURITY.md` and `RESOURCES_EMPTY`, which runbook steps replace.
- `src/prepare.ts`: it runs only in a release copy, a folder with the `.release-copy` file and no `.git`. For each released package, it removes `private`. It writes `license` from the root `package.json`, `repository` from `release/repository.json` with the package folder, and `publishConfig` with public access and provenance, after `version`. It copies the root `LICENSE` into the package folder. Core also gets `authtempo.breaking` from its `CHANGELOG.md` and `authtempo.deprecations` from `release/deprecations.json`. A released package with no `engines` fails.
- `src/dry-run.ts` (`pnpm release:dry-run [--keep] [--at <version>] [--tarballs <folder>]`): it stops with exit 2 on a dirty checkout. It copies `git archive HEAD` into a new temp folder and writes the `.release-copy` file. Then it installs offline and writes one minor changeset for the group. It runs `changeset version`, `prepare`, and the build of the released packages with the cache off. The site build fails on a changelog version with no release date, and the site ships in no tarball. The commands of the release copy are one list, `src/lib/release-copy.ts`, which the job `check` of `release.yml` also runs. `check-workflows` holds each run line of the job to the list. It packs each released package with `--ignore-scripts`, runs `check-pack` on the tarballs, `npm publish <tarball> --dry-run` for each, and `pnpm publish -r --dry-run --ignore-scripts`. The pnpm list must equal the tarball list. Last, the smoke runs in two phases, each in its own copy of `release/smoke/` with the tarballs installed offline. In the apps phase, the copy installs no devDependencies, so no vitest. `smoke.mjs` loads each entry that is not a kit of `release/smoke/kits.json` and runs the CLI. Each kit must fail there for want of its tool, so a main entry that imports vitest fails the run. In the kits phase, the copy installs the devDependencies, and each kit must load. When the checkout is at `0.0.0`, the dry run runs `rewrite-unpublished` in its copy after `changeset version` and before `prepare`. The version branch of the first release does the same. So `check-pack` reads the tarballs of the first release, and a note form that the lists miss fails it. A checkout above `0.0.0` holds no note, so no rewrite runs. The summary line of the rewrite is a note of the dry run. It stops at the first step that fails. It prints one line per tarball (`<name>@<version> <sha256> files=<n>`) and the summary line `release-dry-run: PASS packages=<n> of <n> version=<v> tarballs=<n> files=<f> smoke=<k> failures=0`. Each publish call has `--dry-run` and the registry `http://127.0.0.1:9`, where nothing listens, also as the `@authtempo` scope registry. Each child gets `PATH`, `HOME`, `TMPDIR`, and `LANG` from your env, and no other key of it. `NPM_CONFIG_USERCONFIG` and `NPM_CONFIG_GLOBALCONFIG` name two empty files in the temp folder, so no npmrc and no token reaches a child. The run fails when an npm or pnpm line names another registry. It never commits, tags, or pushes. It deletes the temp folder unless you give `--keep`.
- With `--at <version>`, the copy packs `HEAD` at its own version. The run writes no changeset, runs no `changeset version`, and runs no rewrite. It fails when the group version differs. Use it on the commit of a tag: without it, the dry run packs the next minor.
- With `--tarballs <folder>`, the run makes no copy, versions nothing, and packs nothing. It runs `check-pack`, both publish dry runs, and the smoke on the tarballs of the folder. It runs only in a release copy, because `pnpm publish -r` reads the manifests of `prepare`. The job `check` of `release.yml` runs it on its tarballs after `check-pack`, so the smoke reads the bytes that npm receives.
- `src/rehearse.ts` (`pnpm release:rehearse [--keep]`): the rehearsal of the version pull request, before step 2 of "At each release" in `docs/release/RUNBOOK.md`. It stops with exit 2 on a checkout with changes, but `release/rehearsal.json` may change. It clones the last commit into a new temp folder and installs offline. Then it runs `changeset version`, and at `0.0.0` the rewrite of the first release. It writes the edits of the runbook from `release/rehearsal.json`. These are the rows of `RELEASE_DATES`, the support rows and their table, and the Resources rows. At the first release, it also removes the owner check of the routes page. `HAND_EDITS` names the scripted edit of each text that the owner writes by hand. Then it runs `pnpm format` and `release-check --no-osv --no-dry-run --base <commit>` in the copy, through the test servers of the copy. It takes those servers down at the end. It stops at the first step that fails. The summary line is `release-rehearsal: PASS version=<v> first=<yes|no> dates=<n> support=<n> resources=<n> removed=<n> release-check=PASS failures=0`, and the failure lines of `release-check` follow it. It never commits, tags, or pushes. It deletes the temp folder unless you give `--keep`.
- `src/check-dependencies.ts`: each direct dependency of each workspace package and of the root package has one row in `release/dependencies.json` for each kind: `runtime`, `peer`, or `dev`. Each row lists the versions and the users that the manifests hold, a reason, and a read date. A runtime row also names its seam. The runtime closure of the released packages comes from `pnpm-lock.yaml` and the license of each installed package. It holds only MIT, ISC, BSD-2-Clause, BSD-3-Clause, Apache-2.0, and 0BSD, or a package of `release/license-exempt.json`.
- The check also reads `pnpm-workspace.yaml`. `minimumReleaseAge` stays at 1440 or more. Each `minimumReleaseAgeExclude` entry names a row, as `<name>` or `<name>@<version>`, so a pattern such as `*` fails. Each `allowBuilds` entry has its own reason comment, in block form or in flow form. `dangerouslyAllowAllBuilds`, `overrides`, `packageExtensions`, `patchedDependencies`, `catalog`, and `catalogs` fail while present: no rule reads them yet. The keys `pnpm` and `resolutions` of the root `package.json` also fail while present, for the same reason.
- `src/check-osv.ts`: sends the name and version of each package of that closure to the OSV batch query. It fails on an advisory with no live exemption in `release/osv-exempt.json`, and when OSV gives no answer. When `OSV_URL` names another server, the check prints a note under the summary line. Only the owner writes an exemption.
- `src/release-check.ts` (`pnpm release:check [--no-osv] [--no-dry-run] [--base <ref>]`): the release check of spec 33 item 12. It runs four steps in order, and it stops at the first step that fails. Step 1 is the evidence run `pnpm turbo run test typecheck typecheck:configs --force --continue --log-prefix=task`, through the test servers of the checkout. The flag keeps the `<package>:<task>: ` prefix of each line on a GitHub runner, and a log with a `::group::` task and no prefix fails. The Turbo summary must read `0 cached`, and each task must pass. It reads each summary line only at the start of a line, and two summaries fail. A `Failed:` line or an `ERROR` line of Turbo fails too. Each workspace package with a `test` script has its `<package>:test` block, with a summary line and no failure. Each package with a `typecheck` script has its block. Each failure count comes from a summary line. A vitest summary with 0 passed tests fails, also when each test skipped. The oldest file of each released `dist` is newer than the newest file of its `src`. Step 2 reads the conformance counts in the same log. Each suite passes each test, and each package that runs the reporter reports a suite. Step 3 runs each check above that runs alone, and it reads `check-security-policy` from the site run. `CHECK_EXEMPT` names each other `src/check-*.ts` with its reason, and a test holds both lists to the folder. Step 3 also runs each proof test of `UNPUBLISHED_CODE` by its title, and the proof must pass one test. `--base` gives the ref of `check-changesets` and `check-records`. Step 4 is the dry run, with one SHA-256 line for each released package, matched by name. `--no-osv` and `--no-dry-run` skip a step, and the summary line counts it as not run. An `OSV_URL` other than the OSV batch query fails. The summary line is `release-check: PASS tasks=<n> of <n> cached=0 packages=<p> of <p> checks=<c> of <c> dry-run=PASS load=<l> failures=0`, and the notes give the uptime and the load.

The forbidden names are one list, `FORBIDDEN_PACK_NAMES` in `src/lib/pack-rules.ts`. Each older `proof/pack-files.mjs` imports it through `forbiddenMatch`, so a new name reaches every proof.

Each git test makes its own repository in the temp folder (`TMPDIR`) and never reads the history of this repository.

Run a check from the repository root. The `ref` is `main` when you give none:

```sh
node scripts/release/src/check-packages.ts
node scripts/release/src/check-changesets.ts [ref]
node scripts/release/src/check-records.ts [ref]
node scripts/release/src/check-support.ts
node scripts/release/src/check-workflows.ts
node scripts/release/src/check-deprecations.ts [version]
pnpm release:check [--no-osv] [--no-dry-run] [--base <ref>]
```

Run the tests with the cache off:

```sh
pnpm turbo run test typecheck --filter=authtempo-release --force
```

## A new workspace package

Put the package in exactly one list. To release it, add its name to `fixed[0]` of `.changeset/config.json`. To keep it unreleased, add its name to `ignore` of `.changeset/config.json` and to `release/unreleased.json` with one reason. `check-packages` fails until the package is in one list. A released package also needs its entry in `release/pack-needs.json`: the check-pack test fails until it exists.

## A new dependency

Add one row to `release/dependencies.json` for each new name and kind, or add the new user and version to the row that exists. Read the version, the license, and the install script with `npm view <name>@<version> license scripts time --json`. Write the date of the read in `read`, in the form YYYY-MM-DD. A runtime row names the file that holds each import in `seam`. `check-dependencies` fails until the row matches the manifests.

A package of the runtime closure with an `os`, a `cpu`, or a `libc` field in `pnpm-lock.yaml` is a platform package. pnpm skips it on a machine of another platform, so the check cannot read its package.json there. Give it a `platform` row with `name`, `versions`, `license`, `reason`, and `read`, and no users. Name the source of the license in the reason. The check fails on a skipped platform package with no row. It also fails on a row that disagrees with an installed package.json, or that matches no platform package of the closure.

## The exemption files

`release/license-exempt.json` lists each package of the runtime closure that has a license outside the allow list. Each entry has `name`, `version`, `license`, `reason`, and `read` (YYYY-MM-DD). An entry matches one name, one version, and one license exactly. An entry that matches no package of the closure fails.

`release/osv-exempt.json` lists each open advisory that the owner accepts. Each entry has these fields:

- `id`: the OSV id of the advisory.
- `name` and `version`: the package of the closure.
- `reason`: why the advisory does not apply.
- `read`: the date that the owner read the advisory (YYYY-MM-DD), on or before the day of the run.
- `expires`: the last day of the exemption (YYYY-MM-DD), on or after `read`, and at most 90 days after it.

An entry that has expired, or that matches no package of the closure, fails. An entry fails as stale when OSV did not return its advisory id for its package and version.
