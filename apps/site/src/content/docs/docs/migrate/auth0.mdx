**For:** an operator and a developer who move an app from Auth0 to authtempo.

**What it does:** you import the user export of Auth0 and its hash file into core's tables, and change the app's Auth0 calls to `@authtempo/client`.

## Before you start

- An API with authtempo and `password` set. Do a [getting started tutorial](/docs/start/) first.
- The user export job of Auth0, `POST /api/v2/jobs/users-exports` with the format `json`. [The command](/docs/reference/import-cli/#the-command) reads its file.
- The password hashes, if you need them. Auth0 sends them only through a support case, as a PGP file. [The command](/docs/reference/import-cli/#the-command) reads them with `--hashes`.
- `@authtempo/cli` and `@authtempo/legacy-hashes` in the app's workspace. [authtempo import](/docs/reference/cli/import/) is a command of the first.

## Steps

### Export

1. Run the user export job, and decompress the file if it is compressed, for example with `gunzip users.ndjson.gz`.
2. Decrypt the hash file of the support case as `hashes.ndjson`.
3. For organizations, write `organizations.json`: one array of `GET /api/v2/organizations` objects, each with a `members` array.

### Carry the passwords

1. Chain the legacy seam before core's PBKDF2 in the API. Pass `["bcrypt"]` as `formats`.

### Dry run

1. Map your role names to core's roles with `--role-map`. Auth0 roles have no default map.
2. Run the import as a dry run, and read the report.
3. Check the `hashes:` line against `--formats`. It counts the hash formats of the export, such as `hashes: bcrypt 812, none 31`.

The `@authtempo` packages are on npm. Add the CLI to your app with `pnpm add -D @authtempo/cli`, and run each command as `pnpm exec authtempo …`.

```sh
authtempo import auth0 --users users.ndjson --hashes hashes.ndjson --organizations organizations.json --role-map lead=admin --formats bcrypt --target postgres --url-env DATABASE_URL --dry-run
```

### Move

Run the real import on a copy of the database only. The one real import into the real database runs at step 9 of [The cutover](/docs/migrate/cutover/), after the old sign-ins stop. If it runs earlier, a password, an address, or a delete that changes in the old system after it is lost. [One real import](/docs/migrate/cutover/#one-real-import) tells why.

1. Make the copy. On Postgres, create an empty database, set `COPY_URL` to its URL, and load the real one into it with `pg_dump --no-owner "$DATABASE_URL" | psql "$COPY_URL"`.
2. On D1, load the real database into the empty local copy of the import Worker with `wrangler d1 export <database> --remote --output copy.sql` and `wrangler d1 execute <database> --local --file copy.sql`.
3. Run both in the folder of the import Worker. Delete its `.wrangler/state` first, or the load stops on a table that exists.
4. Run the same command without `--dry-run`, with `--url-env COPY_URL`. On D1, run the import Worker without `"remote": true`, so it writes the local copy.

```sh
authtempo import auth0 --users users.ndjson --hashes hashes.ndjson --organizations organizations.json --role-map lead=admin --formats bcrypt --target postgres --url-env COPY_URL
```

### Verify

1. Run `authtempo import verify` with the same files on the copy. It exits 0 only when the copy holds the whole export.
2. Run `authtempo check <base url>` against the API.
3. Sign in once with a known user and the old password, and once by each other method of the app. Do it at step 13 of [The cutover](/docs/migrate/cutover/): before that step, the real database holds no user.
4. Drop the copy, and on D1 delete `copy.sql`, when `import verify` exits 0. The copy holds every user of the export.

```sh
authtempo import verify auth0 --users users.ndjson --hashes hashes.ndjson --organizations organizations.json --role-map lead=admin --formats bcrypt --target postgres --url-env COPY_URL
authtempo check https://api.example.com
```

## The calls

Auth0 sends the person to its own page. authtempo has no page for a web app: the app shows its own sign-in form.

| Auth0 | authtempo |
| --- | --- |
| `loginWithRedirect()` | The app's own form, with `client.magicLink.request` or `client.password.signIn`. |
| `loginWithRedirect({ authorizationParams: { connection: "google-oauth2" } })` | Send the browser to `/auth/social/google/start?next=/` on the API. |
| `logout()` | `client.signOut()` |
| `getUser()`, `isAuthenticated()` | `client.session()` |
| `getTokenSilently()` | `client.jwt.token()` |
| The check of an Auth0 access token on the server | `auth.session(request)`, or a check of the session JWT against `/auth/jwks` |

## How it behaves

- A hash line is used only when exactly one user matches `auth0|<_id>` and the addresses are equal.
- Only a `$2a$` or `$2b$` hash imports. Any other hash is refused by its format.
- An unmapped role becomes `member`. An organization with no owner gets its first admin as owner; with no admin it is skipped.
- A `github` identity imports as GitHub. Every `linkedin` identity is listed as `identity:linkedin_legacy`.
- A user with a `blocked` value other than `false` is skipped as `banned`.
- Without `--hashes`, the command prints one line and imports no password. A reset or a magic link then signs each user in.

:::caution
Warning: the decrypted hash file holds every password hash. Do not commit it, and delete it after the run.
:::

## If it fails

- The command exits 1: read the report for `unmatched_row`, `hash_email_mismatch`, `no_owner`, or a refused hash.
- The command stops at start: `organizations.json` is the page object of the API, not the array. Save the array itself.
- [`invalid_credentials`](/docs/reference/errors/#invalid_credentials): the password is wrong, or the user imported with no password.
