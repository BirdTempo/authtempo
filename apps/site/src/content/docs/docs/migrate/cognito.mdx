**For:** an operator and a developer who move an app from Amazon Cognito to authtempo.

**What it does:** you import the users of a Cognito user pool. Cognito exports no hash, so core asks Cognito once, at each user's first password sign-in, and then keeps its own hash.

## Before you start

- An API with authtempo. Do a [getting started tutorial](/docs/start/) first.
- The AWS CLI, with read access to the user pool.
- An app client of the pool that lists `ALLOW_USER_PASSWORD_AUTH` in its auth flows. `password.legacyVerify` of [Passwords](/docs/reference/config/#passwords) calls it.
- A pool that accepts the address as a user name or as an alias. `password.legacyVerify` of [Passwords](/docs/reference/config/#passwords) sends the address.
- `@authtempo/cli` and `@authtempo/legacy-hashes` in the app's workspace. [authtempo import](/docs/reference/cli/import/) is a command of the first.

## Steps

### Export

1. Export the users, and keep the whole output with its `Users` array.

```sh
aws cognito-idp list-users --user-pool-id "$POOL" --output json > users.json
```

### Carry the passwords

Cognito exports no hash. Core checks each password against Cognito once, at the user's first password sign-in.

2. Pass `clientSecret` too, when the app client has a secret.
3. On Workers, pass `waitUntil`, so the failure line outlives the response.

### Dry run

1. Run the import as a dry run, and read the report.
2. Cognito exports no hash, so the `hashes:` line counts `legacy-verify` markers and `none` only.

The packages are not on a registry yet. In this repo, run each command below as `node /path/to/authtempo/packages/cli/dist/bin/authtempo.js …` in the folder of your app. [Run it from this repo](/docs/reference/cli/#run-it-from-this-repo) tells how. The pnpm filter form runs in `examples/worker` and exits 1 on any failure, so use it for `--help` only.

```sh
authtempo import cognito --users users.json --legacy-verify --target postgres --url-env DATABASE_URL --dry-run
```

### Move

Run the real import on a copy of the database only. The one real import into the real database runs at step 9 of [The cutover](/docs/migrate/cutover/), after the old sign-ins stop. If it runs earlier, a password, an address, or a delete that changes in the old system after it is lost. [One real import](/docs/migrate/cutover/#one-real-import) tells why.

1. Make the copy. On Postgres, create an empty database, set `COPY_URL` to its URL, and load the real one into it with `pg_dump --no-owner "$DATABASE_URL" | psql "$COPY_URL"`.
2. On D1, load the real database into the empty local copy of the import Worker with `wrangler d1 export <database> --remote --output copy.sql` and `wrangler d1 execute <database> --local --file copy.sql`.
3. Run both in the folder of the import Worker. Delete its `.wrangler/state` first, or the load stops on a table that exists.
4. Run the same command without `--dry-run`, with `--url-env COPY_URL`. On D1, run the import Worker without `"remote": true`, so it writes the local copy.

```sh
authtempo import cognito --users users.json --legacy-verify --target postgres --url-env COPY_URL
```

### Verify

1. Run `authtempo import verify` with the same files on the copy. It exits 0 only when the copy holds the whole export.
2. Run `authtempo check <base url>` against the API.
3. Sign in once with a known user. Sign in once more with a user whose Cognito address has capital letters. Do it at step 13 of [The cutover](/docs/migrate/cutover/): before that step, the real database holds no user.
4. Drop the copy, and on D1 delete `copy.sql`, when `import verify` exits 0. The copy holds every user of the export.

```sh
authtempo import verify cognito --users users.json --legacy-verify --target postgres --url-env COPY_URL
authtempo check https://api.example.com
```

## The calls

| Amplify | authtempo |
| --- | --- |
| `signIn({ username, password })` | `client.password.signIn({ email, password })` |
| `signUp({ username, password })` | `client.password.signUp({ email, password })` |
| `signInWithRedirect({ provider: "Google" })` | Send the browser to `/auth/social/google/start?next=/` on the API. |
| `resetPassword({ username })` | `client.password.requestReset({ email })` |
| `confirmResetPassword(input)` | `client.password.reset({ token, password })`, with the token of the reset link |
| `signOut()` | `client.signOut()` |
| `getCurrentUser()`, `fetchAuthSession()` | `client.session()` |
| The ID token of `fetchAuthSession()` | `client.jwt.token()` |

## How it behaves

- Only a `CONFIRMED` user gets the marker. Every other status skips the user, and the reason names the status.
- Only the built-in providers `Google` and `SignInWithApple` map to an identity.
- Core calls Cognito only for a user whose password row holds the marker. A right answer writes core's own hash over it.
- Every failed password sign-in answers no earlier than `timeoutMs`. So the response time does not show an address that is not yet migrated.
- A claim of the address deletes the marker, and a reset overwrites it.
- Each Cognito challenge answers false, the second factor and `NEW_PASSWORD_REQUIRED` among them. Such a user resets the password.

:::caution
Warning: a wrong region, app client, or auth flow fails every imported user. Sign in once with a known user before the cutover.
:::

## If it fails

- [`invalid_credentials`](/docs/reference/errors/#invalid_credentials) for every user: the app client does not allow `USER_PASSWORD_AUTH`, or the pool does not take the address as a user name. The log line names the Cognito error.
- The command exits 1 with `legacy-verify` refusals: the run has no `--legacy-verify`.
- The command stops at start: `users.json` holds a bare array. Save the whole `list-users` output.
