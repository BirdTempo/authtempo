**For:** a developer whose app runs Better Auth 1.7 and must keep its code and its tables.

**What it does:** the Better Auth package names point at `@authtempo/compat-better-auth`. The app's code then runs on the engine of authtempo, on the app's own Better Auth tables.

:::caution
Warning: upgrade Better Auth to 1.7.7 or later before the move. Version 1.7.7 fixed a magic link takeover, and the old system stays the rollback target during the move.
:::

## Before you start

- An app on Better Auth 1.7, on Postgres through postgres.js or on D1. [Better Auth compatibility](/docs/reference/compat-better-auth/) lists what it keeps.
- The tables `user`, `session`, `account`, `verification`, `organization`, `member`, `invitation`, and `passkey`. Create a missing table with Better Auth's own SQL for it. [The Better Auth tables](/docs/reference/schema/#the-better-auth-tables) section lists them.
- The packages of authtempo in the pnpm workspace of the repo. [Choose your stack](/docs/start/) tells why.

## Steps

### Export

Nothing leaves the database: the app keeps its own tables.

1. Back up the database before the move, with `pg_dump` on Postgres.
2. On D1, back it up with `wrangler d1 export <database> --remote --output backup.sql`.

### Carry the passwords

The password rows stay in the `account` table. Core verifies a Better Auth hash, and rehashes it as PBKDF2 at the first right sign-in.

### Dry run

1. List the compat migrations that the database lacks, and apply nothing.
2. Add `--before-1.7` on D1 when the tables are from before Better Auth 1.7.

The packages are not on a registry yet. In this repo, run each command below as `node /path/to/authtempo/packages/cli/dist/bin/authtempo.js …` in the folder of your app. [Run it from this repo](/docs/reference/cli/#run-it-from-this-repo) tells how. The pnpm filter form runs in `examples/worker` and exits 1 on any failure, so use it for `--help` only.

```sh
authtempo migrate --target postgres --url-env DATABASE_URL --tables compat --dry-run
authtempo migrate --target d1 --database <database> --remote --tables compat --dry-run
```

### Move

1. Run the same command without `--dry-run`.
2. On D1, the command copies each compat file of the table below into the app's `migrations_dir`, under the next number. Then it applies them.
3. On Postgres, the server can call `betterAuthSchemaStorage({ dialect: "postgres", sql }).migrate()` once per deploy, before the first request, instead.
4. In the app's `package.json`, point each Better Auth name that the app imports at the compatibility package.

```json
{
  "dependencies": {
    "better-auth": "npm:@authtempo/compat-better-auth@0.0.0",
    "@better-auth/drizzle-adapter": "npm:@authtempo/compat-better-auth@0.0.0",
    "@better-auth/expo": "npm:@authtempo/compat-better-auth@0.0.0",
    "@better-auth/passkey": "npm:@authtempo/compat-better-auth@0.0.0",
    "@better-auth/api-key": "npm:@authtempo/compat-better-auth@0.0.0",
    "@authtempo/core": "0.0.0",
    "@authtempo/client": "0.0.0",
    "@authtempo/handoff": "0.0.0",
    "@authtempo/adapter-d1": "0.0.0",
    "@authtempo/adapter-postgres": "0.0.0"
  }
}
```

5. Keep both adapters in the list, also for an app on one database. The server entry loads both.

### Verify

1. Run `authtempo check <base url>` against the API.
2. Sign in once with a known user by each method: the password, the magic link, and each social provider.

```sh
authtempo check https://api.example.com
```

### Change the calls

1. Core stores no provider access token (spec 9). So `getAccessToken` has no answer, and each caller of it breaks at the cutover. Move each call to the provider's own token flow before the move.
2. The session cookie is `__Host-tempo_session` (plan 12b), and a browser never sends a `__Host-` cookie to a sibling subdomain. So `advanced.crossSubDomainCookies` has no map, and an app that shares its session across subdomains breaks at the cutover.
3. Remove each import of `better-auth/db`, `better-auth/types`, and the access subpaths. The package does not export them.
4. Start the server once. Read the list of the one `BetterAuthCompatError`, and change or remove each option that it names.

The account operations of a settings page work on the shim. They need a fresh session for each sensitive change. [The account operations](/docs/reference/compat-better-auth/#the-account-operations) lists them and their options. [Build an account settings page](/docs/guides/account-settings/) shows the client calls and the fresh rule.

5. Wrap the handler in place of `hooks`. Core has no request hooks.

### Cut over

:::caution
Warning: upgrade Better Auth to 1.7.7 or later before the move. Version 1.7.7 fixed a magic link takeover, and the old system stays the rollback target during the move.
:::

1. Do the steps of [The cutover](/docs/migrate/cutover/).
2. Register the new callback URL at each social provider before the cutover.
3. With the admin plugin, carry the admins. Core gives operator power by the platform role only, never by Better Auth's `role` column.
   - Make one admin the first operator, once, with `auth.tempo.api.operator.createAdmin` in the app. It makes the platform organization.
   - Grant the platform role to each other admin with `auth.tempo.api.operator.platformRole.grant`, or with `/admin/set-role` from the first operator's session.
   - Ask each admin to sign in again and turn a second factor on. A session from before the grant holds no operator power.
   - Skip this step, and each admin loses the admin power at the cutover: each admin call answers 403.
   - The `authtempo` option takes no operator secret, so the CLI's `create-admin` and `users` commands do not reach the app.

The bans of the admin plugin need no step. Compat migration 0009 copies each ban into core's columns, so a banned user stays banned.

## The D1 files

| File | What it does |
| --- | --- |
| `0001_compat_better_auth.sql` | Adds `ta_meta` and `ta_limit`, the `ta` columns that Better Auth lacks, and the unique keys that core needs. |
| `0002_compat_schema_v5.sql` | Moves the version to 5. It changes no table. |
| `0003_compat_schema_v6.sql` | Adds `ta_totp` and `ta_trusted_device`. |
| `0004_compat_schema_v7.sql` | Adds `ta_jwk`, `ta_oauth_client`, `ta_oauth_consent`, and `ta_oauth_token`. |
| `0005_compat_schema_v8.sql` | Adds `ta_second_factor`, copies each enabled `ta_totp` row, and deletes each setup that no enable confirmed. |
| `0006_compat_schema_v9.sql` | Adds `secret_version` to `ta_totp`, `ta_second_factor`, and `ta_jwk`, and `taSecretVersion` to `verification`, default 1. Tables with other names take the text of `compatMigration0006Sql("sqlite", storage.names)`. |
| `0007_compat_schema_v10.sql` | Adds `taFreshAt` to `session`, nullable, with no fill. Tables with other names take the text of `compatMigration0007Sql("sqlite", storage.names)`. |
| `0008_compat_schema_v11.sql` | Adds the version 11 columns to `ta_oauth_client` and `ta_oauth_token`, and adds `ta_oauth_device`, `ta_oauth_subject`, `ta_oauth_session_client`, and `ta_oauth_logout`. The same text for every naming. |
| `0009_compat_schema_v12.sql` | Adds `taBannedAt`, `taBanReason`, and `taBanUntil` to `user` and `taActorId` to `session`, nullable, and adds `ta_operator_audit`. It copies each ban of the admin plugin into the three ban columns. Tables with other names take the text of `compatMigration0009Sql("sqlite", storage.names)`. |
| `0010_compat_schema_v13.sql` | Adds `activeTeamId` to `session` and `teamId` to `invitation`, nullable, with no fill. Creates Better Auth's `organizationRole` when it is absent, and adds `taRank` (default 1) and the unique key on (`organizationId`, `role`). Creates Better Auth's `team` and `teamMember` when they are absent. Adds `teamMember.taOrganizationId` and `taUpdatedAt` with a fill, and the unique key on (`teamId`, `userId`). Adds core's `ta_api_token`, `ta_organization_token`, and `ta_moved_token`. The `d1-before-1.7` file also adds `team.memberCount` (default 0) and `teamMember.membershipKey` (unique), which the team tables of Better Auth 1.4.21 lack. Tables with other names take the text of `compatMigration0010Sql("sqlite", storage.names)`, with `"before-1.7"` as the third argument for tables from before 1.7. |

A file number lower than the Better Auth table migration makes every new database fail at the compat file with `no such table`.

Better Auth's `teams` option adds `session.activeTeamId` and `invitation.teamId`. SQLite has no `ADD COLUMN IF NOT EXISTS`, so the shipped 0010 fails on these tables with `duplicate column name: activeTeamId`. An app with these two columns writes its own 0010 file. It is the shipped file of its directory without its two `ALTER TABLE ... ADD COLUMN` lines of `session` and `invitation`. The other lines must stay. They create the `organizationRole`, `team`, and `teamMember` tables when they are absent. They add `taRank`, the `ta` columns, and the unique keys, and move the versions.

The app applies the files to 0009 and its own 0010 with `wrangler d1 migrations apply` before `authtempo migrate --target d1 --tables compat`. Then the compat version is 10, and the command copies nothing. On Postgres, the 0010 adds each column only when it is absent, so no own file is necessary.

The table prefix `ta_` keeps the old product name tempo-auth for compatibility. [Schema and migrations](/docs/reference/schema/) states the rule.

## Cutover of API tokens

The `apiKey` plugin maps onto core's API tokens. Better Auth stores the SHA-256 of the whole key. So `moveBetterAuthApiKeys` moves each key into core's token table, and the key keeps working under the same secret. A new key has core's prefix, `tk_` for a user or `to_` for an organization. Each step states what breaks without it.

1. Before the cutover, copy the database. Apply the compat migrations to the copy: `storage.migrate()` on Postgres, or the D1 files with `wrangler d1 migrations apply`. Without them, the storage refuses the copy with `schema_mismatch`, and the dry run cannot start. Then run `moveBetterAuthApiKeys` with `dryRun: true` against the copy. On D1, run it in a Worker with the D1 binding, as the compat package README shows. A stored prefix outside `movedPrefixes`, or a row with no prefix, makes the dry run throw `BetterAuthCompatError`. The error names each such prefix and counts the rows with no prefix. Do step 2 for each, and run the dry run again. Else the report gives the count of keys per owner and the stored prefixes. Without it, you do not know whom to tell, or which prefixes to list.
2. Put each stored prefix other than `defaultPrefix` in `authtempo.movedKeyPrefixes`. Re-issue each key with no prefix, and delete its row. Without it, the move throws before its first write and moves nothing. Pass `movedPrefixes: movedKeyPrefixesOf(options)` to the move, so it reads the list that core reads.
3. Tell each owner whose key the report skips. `skippedKeys` names each row id, its owner, and the reason. The reasons are `disabled`, `expired`, `noDigest`, `noCreator`, `noOwner`, `invalidName`, `invalidMetadata`, and `wideWindow`. `noDigest` is a key with no digest. `noCreator` is an organization key with no creator and no owner. `noOwner` is a key whose user or organization is gone. `invalidName` is a name over 80 characters or with a control character. `invalidMetadata` is metadata over 4096 bytes. `wideWindow` is a window that core cannot hold without a wider rate. It has a max below 1, or less than one call a day. A key with no name moves with the name `Moved key`. `present` is a row that an earlier run moved. After the cutover each other skipped key answers 401 `token_retired`, and every script that uses one stops.
4. Deploy the shim build with the compat migration 0010. Without the migration, the storage refuses to start with `schema_mismatch`. From the deploy to the end of step 5, every old key answers 401 `token_retired`. This gap is an outage of each script with an old key, so keep it short. Run step 5 right after the deploy.
5. Run `moveBetterAuthApiKeys` with `dryRun: false`. On D1, run it in a Worker with the D1 binding, as the compat package README shows. It records each moved row in `ta_moved_token`, so a second run skips it, and a revoked key stays revoked. Without it, every old key answers `token_retired` by its prefix, and the key list shows no row for it.
6. A resource server with `@authtempo/verify` passes `movedPrefixes`, the same list. It passes `movedKind`, with that kind in `accept`: `"api-token"` for `references: "user"`, `"organization-token"` for `"organization"`. Without them, the verifier answers null for every moved key.
7. Change the app code that reads the `apikey` table itself, and each check of the old prefix. Without it, a new `to_` key never authenticates, and the key list shows only the old table.
8. When every owner moved, drop the `apikey` table yourself. No migration of authtempo drops it, because it is your record.

A moved key counts against the cap of 50 live tokens per owner, because it acts.

## How it behaves

- Better Auth's defaults apply: a session lives 7 days and refreshes after 1 day.
- The session cookie is `__Host-tempo_session`, not `better-auth.session_token`. Change each test and each legal page that names the old cookie. For one release the shim also reads `tempo_session`, the name before plan 12b, and the handler moves it. On Expo, `getCookie()` answers `__Host-tempo_session=<token>`, and the storage key keeps the name `<storagePrefix>_tempo_session`.
- The cookie name keeps the old product name tempo-auth for compatibility. [Cookies](/docs/reference/cookies/) states the rule.
- The one key that is not Better Auth's is `authtempo`. `authtempo.appURL` is the origin where each sign-in lands, by default the origin of `baseURL`. An absolute `callbackURL` off that origin answers 403 with `INVALID_CALLBACK_URL`. `authtempo.passwordHash` replaces `betterAuthPasswordHash()`.
- `session.token` holds the SHA-256 of the token. App SQL that reads it reads a hash.
- A reset ends every session, where Better Auth kept the others.
- `requireEmailVerification: true` maps to `password.requireVerified`. An unverified sign-in answers `EMAIL_NOT_VERIFIED` and gets a new verify link, also when `sendOnSignIn` is absent.
- `secrets: [{ version, value }]` maps to core's `secrets`. Version 0 is refused: renumber from 1. With `secret`, version 1 must be the value of `secret`. The shim does not read `BETTER_AUTH_SECRETS`.
- `autoSignIn: false` is refused unless `requireEmailVerification` is true. The sign-up answer stays Better Auth's: a session unless `requireEmailVerification` is true, and `USER_ALREADY_EXISTS` for a taken address.
- Core refuses a secret under 32 characters, and a current secret under an estimated 100 bits of entropy, at start. Better Auth only warns.
- `disableSignUp` maps to core's `signUp: false` only when every method and social provider that creates a user sets it. A mix is refused at start. A provider's `disableImplicitSignUp` is refused.
- Users, social accounts, passwords, organizations, members, and passkeys carry over. A password rehashes to PBKDF2 at its first right sign-in.
- The callback URL at each provider is `<baseURL><basePath>/social/<provider>/callback`, not `/api/auth/callback/<provider>`.
- The plugins `jwt`, `mcp`, `cimd`, `oidc-provider`, and `oauth-provider` are refused. A JWT that Better Auth issued stops verifying at the cutover.
- The user ids of Better Auth carry over. A user id must never be a `cl_` value or an https URL, because a client id has that form. `@authtempo/verify` reads an access token whose `sub` equals its `client_id` as a client with no person. Keep a custom Better Auth id generator to this rule before the app turns on core's provider.
- A Better Auth path that the app calls with its own `fetch` answers 404. Call the client method instead. The account paths and the email code paths are served in Better Auth's shapes.
- A revoke, the change of address, the link, the unlink, and the delete need a fresh session. `session.freshAge` sets the window, and `0` is refused. A stale session answers `SESSION_NOT_FRESH` with 403.
- `/two-factor/disable`, `/two-factor/get-totp-uri`, and `/two-factor/generate-backup-codes` need a fresh session too, checked before the password.
- Better Auth's `list-sessions` needs a fresh session. On authtempo the list needs a session only, as core's `GET /sessions` does.
- A social link needs the provider's verified address, equal to the account's. Better Auth also links an unverified address of a trusted provider, and a different address with `allowDifferentEmails`. On authtempo the callback answers `email_mismatch` for a different address, and both options are refused at start.
- `user.deleteUser.enabled` stays off by default, as in Better Auth. An organization where the user is the last owner and other members remain stops the delete with `SOLE_OWNER`.

:::caution
Warning: a `secret` other than the app's value locks every user with the second factor out of it. Keep the `secret` that the app has. Change it later with the steps on [Secrets](/docs/operations/secrets/).
:::

## If it fails

- `BetterAuthCompatError` at start: change each option in its list.
- `relation "ta_limit" already exists`: the schema holds the tables of the Postgres adapter. Run the compatibility storage on a schema without them.
- `no such column: issuer` on D1: the 1.7 file ran on tables from before Better Auth 1.7. The failed run left its compat copies in `migrations_dir`. Delete each copy whose name ends in `_compat_better_auth.sql`, or in `_compat_schema_v5.sql` to `_compat_schema_v10.sql`. Then run the command again with `--before-1.7`.
- `duplicate column name: memberCount` on D1: the `d1-before-1.7` 0010 ran on the team tables of Better Auth 1.7. Use the `d1` file.
- [`invalid_token`](/docs/reference/errors/#invalid_token): a magic link, an invitation, or a delete link from before the cutover. Send it again.
- [`token_retired`](/docs/reference/errors/#token_retired): an old Better Auth key that did not move, because Better Auth held it disabled, expired, or with no digest. Create a new key.
