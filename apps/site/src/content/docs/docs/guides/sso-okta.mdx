**For:** an app developer, or the Okta admin of a customer, who connects the customer's Okta org to an organization.

**What it does:** this page gives the steps in the Okta Admin Console for an OIDC connection and for a SAML connection. Each field name is the name on the Okta pages that the last table lists, with the date of each read.

## Before you start

- A verified domain of the organization, by the steps of [Enterprise SSO](/docs/guides/sso/).
- An Okta admin of the customer who may create app integrations ([Okta help](https://help.okta.com/en-us/content/topics/apps/apps_app_integration_wizard_oidc.htm)).

## Steps

Pick one kind. OIDC needs fewer values.

### OIDC

1. In the Admin Console, go to "Applications and Resources" > "Applications".
2. Select "Create App Integration", then "OIDC - OpenID Connect", then "Web Application".
3. Under "Grant type", keep "Authorization code".
4. Under "Assignments", pick the people or groups that may sign in.
5. Save. Copy the "Client ID".
6. Under "Client authentication", select "Client secret", and copy the secret. Set the method of the secret to `client_secret_post`: the field `token_endpoint_auth_method` of the app in the Okta Apps API.
7. Create the connection with the Okta domain and the values of steps 5 and 6, as `oktaOidc` below does.
8. In "Sign-in redirect URIs", enter `<baseURL><basePath>/sso/<connectionId>/callback`.

The issuer is the org authorization server: `https://<your Okta domain>`. Core reads its discovery document at `/.well-known/openid-configuration`.

Core sends the client secret in the body of the token request, the method `client_secret_post`. Core does not yet send it as HTTP Basic, the method `client_secret_basic`. Okta gives a new app `client_secret_basic`, and then refuses the token request of each sign-in. So set `client_secret_post` in step 6.

### SAML

1. Go to "Applications and Resources" > "Applications" > "Create App Integration".
2. Select "Classic experience", then "SAML 2.0" as the sign-in method.
3. Enter a name, then go on to the SAML settings.
4. Enter a temporary https URL in "Single sign-on URL" and "Audience URI (SP Entity ID)".
5. Set "Name ID format" to the persistent format.
6. Under "Attribute Statements", add the name `email`, the format "Basic", and the email address as the value.
7. Finish the integration. On the "Sign On" tab, open "View SAML setup instructions".
8. Create the connection with the sign-in URL, the issuer, and the certificate there, as `oktaSaml` below does.
9. Enter the `acsUrl` of the connection in "Single sign-on URL".
10. Keep "Use this for Recipient URL and Destination URL" selected.
11. Enter the `spEntityId` of the connection in "Audience URI (SP Entity ID)".
12. Assign the people of the customer to the app.

Core asks for the persistent `NameID` format when the connection has no `subjectAttribute`. Then core refuses a transient `NameID`. Okta needs the "Name ID format" to match the format of a request that names one.

Under "Show Advanced Settings", the "Assertion Signature" must be signed. Pick an RSA SHA-256 "Signature Algorithm" and the SHA-256 "Digest Algorithm". Core refuses SHA-1.

## How it behaves

- Core verifies the Assertion with the certificate of the connection, never with a key of the document.
- A connection holds one or two certificates. When Okta makes a new certificate, add it to `certificates`, activate it in Okta, then remove the old one.
- Each address must be in a verified domain of the organization. A person of the Okta org with another address gets [`sso_domain_mismatch`](/docs/reference/errors/#sso_domain_mismatch).
- Core refuses an encrypted assertion. Leave "Assertion Encryption" off.

## If it fails

- [`sso_failed`](/docs/reference/errors/#sso_failed): the log line names the step. `exchange` means a failed token request. `audience` means a wrong "Audience URI (SP Entity ID)". `destination` or `subject_confirmation` means a wrong "Single sign-on URL". `address` means no attribute `email`. `subject` means a `NameID` that is not persistent.
- [`sso_domain_mismatch`](/docs/reference/errors/#sso_domain_mismatch): the attribute `email` holds an address outside the verified domains.
- [`email_required`](/docs/reference/errors/#email_required): the ID token of an OIDC sign-in holds no address.
- [`sso_not_configured`](/docs/reference/errors/#sso_not_configured): the connection is off, or the config does not turn its kind on.
- [`invalid_body`](/docs/reference/errors/#invalid_body): the connection create refused a value. The message names the field.
