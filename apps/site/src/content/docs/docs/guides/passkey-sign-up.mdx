**For:** an app developer who wants a person to make an account with a passkey only.

**What it does:** `passkey.signUp` adds `POST /passkey/sign-up/options` and `POST /passkey/sign-up/verify`. The verify makes the user, the passkey, and the session. The user has no address.

## Before you start

- Passkey sign-in, as in [Sign in with a passkey](/docs/guides/passkeys/).
- A limiter that counts for the whole deployment: the D1, Postgres, or MySQL limiter. [Limits](/docs/reference/limits/) names each one.
- `signUp: "open"`, the default of [Top level](/docs/reference/config/#top-level).

## Steps

1. Set `passkey.signUp` to `true`, or to an object with `dailyCap`.
2. Pass the limiter of your adapter as `limiter`.
3. Ask the person for a name. Post `{ name }` to `POST /passkey/sign-up/options`.
4. Give the answer to `navigator.credentials.create`.
5. Post `{ response }` to `POST /passkey/sign-up/verify`. A browser gets the session cookie.
6. In a browser app, call `client.passkey.signUp` of the [client package](/docs/reference/client/) in place of steps 3 to 5.
7. On a public site, add the captcha flow `passkey-sign-up` to `captcha.flows`.

## How it behaves

- The options make no user. Core mints the user id at the options and keeps it with the challenge. The verify makes the user.
- The name has 1 to 80 characters, with no control, format, or bidi character. It is the name of the user, and the device shows it with the passkey. The stored passkey has no name until a rename.
- A challenge makes one user. A second verify of the same challenge answers `invalid_token`.
- The verify runs `user.beforeCreate` with `via: "passkey"`, and the session hooks see `via: "passkey"`.
- No second factor gates the sign-up. A new user has no factor, and a passkey with user verification is two factors.
- Only `signUp: "open"` lets the user in. `"invited"` and `false` answer `sign_up_closed`, because an invitation names an address.
- A credential id that another user holds answers `passkey_failed` and makes nothing.
- A live anonymous session of the browser is replaced, as at each sign-in. See [Anonymous sessions](/docs/guides/anonymous/).
- The limit `passkey-sign-up:ip` allows 10 options per IP per hour. The cap `passkey-sign-up:all-day` allows `dailyCap` options per deployment per 24 hours, 1000 by default.
- With the captcha flow on, the captcha runs after the per-IP limit and before the cap. A failed captcha does not count against the cap.
- `createAuth` refuses `passkey.signUp` with a limiter that counts per isolate. For tests only, set `passkey.signUp.isolateLimiter: "allow"`. The cap is then per isolate.
- The user has a proved handle: its passkey. So it can register a second passkey, set a username, and add an address. See [The account with no address](/docs/concepts/account-without-address/).

## Residuals

- A script with a software authenticator can make a user at each verify. The attestation is `none`, so core cannot tell a script from a device. The per-IP limit and the daily cap bound it.
- A script that spends the cap stops real sign-ups until the window ends. Turn on the captcha flow on a public site.
- The user has no address, so no mail can recover the account. Ask the person to register a second passkey or to add an address.

## If it fails

- [`invalid_body`](/docs/reference/errors/#invalid_body): the name is empty, too long, or holds a control character.
- [`sign_up_closed`](/docs/reference/errors/#sign_up_closed): `signUp` is not `"open"`.
- [`rate_limited`](/docs/reference/errors/#rate_limited): the IP made 10 option requests this hour, or the deployment reached the daily cap.
- [`captcha_required`](/docs/reference/errors/#captcha_required), [`captcha_failed`](/docs/reference/errors/#captcha_failed), and [`captcha_unavailable`](/docs/reference/errors/#captcha_unavailable): the captcha flow `passkey-sign-up` refused the request.
- [`passkey_failed`](/docs/reference/errors/#passkey_failed): the response did not verify, or another user holds the credential.
- [`invalid_token`](/docs/reference/errors/#invalid_token) and [`token_expired`](/docs/reference/errors/#token_expired): the challenge is spent or older than five minutes. Start again.
- [`hook_refused`](/docs/reference/errors/#hook_refused) and [`hook_failed`](/docs/reference/errors/#hook_failed): a hook of your app refused the user or threw.
