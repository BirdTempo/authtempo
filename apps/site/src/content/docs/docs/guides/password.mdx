**For:** an app developer who wants people to sign in with an address and a password.

**What it does:** core adds the password routes, a password form on its sign-in page, and `api.password`.

## Before you start

- A working setup from a [getting started tutorial](/docs/start/).
- Workers Paid on Cloudflare. One hash needs more CPU than Workers Free gives one request.

## Steps

1. Add `password: {}` to the config. With no `password` key, the password routes answer 404.
2. Set `password.minLength` when 8 code points is too few for your app.
3. Set `password.breachCheck` to `createBreachCheck()` of `@authtempo/breach-check`. [Check passwords against breaches](/docs/guides/breach-check/) gives the steps.

<Code code={config} lang="ts" title="The password config" />

4. On the sign-up form, call `client.password.signUp({ email, password, name })`.
5. Tell the person to open the link in the mail, in the same browser. The sign-up answers `{ sent: true, signUpProof }` for every address, and the link signs the person in.
6. When the link lands on your app with `password=set`, show a first-password form. It calls `client.password.change({ newPassword })` with no current password.
7. On the sign-in form, call `client.password.signIn({ email, password })`.
8. On the "Forgot password" button, call `client.password.requestReset({ email })`.
9. On a settings page, call `client.password.change({ currentPassword, newPassword })`.

## How it behaves

- The default hash is PBKDF2-HMAC-SHA256 on Web Crypto with 100000 iterations, the highest count that Workers takes.
- A password is 8 to 128 code points. It has no control character, and it does not equal the address.
- Core stores the password as the person typed it, with no Unicode normalization.
- The sign-in takes exactly one of `email`, `username`, or `phone`, with `password`. A body with two of them or none answers `invalid_body`. `username` needs the `username` config. `phone` needs the `phone` config, else `invalid_body`. `phone` is an E.164 number.
- An unknown address, username, or phone runs a dummy hash, so the answer takes the same time. A username or a phone of a bad form does the same, and so does a phone outside `phone.regions`. Every failure answers `invalid_credentials`.
- A username is public, so it tells a guesser which account to try. Each kind of identifier has its own limit, so the limits add up. One account takes up to 20 guesses per 15 minutes by address and username, and 30 with a phone. `password:ip` bounds each IP at 20.
- A reset ends every session of the user. A change ends every other session. Neither deletes an API token.
- A reset of a user with the second factor on sets the password and answers a challenge, not a session.
- A user with the second factor on gets a challenge from the sign-in and from a reset, not a session. [Turn on the second factor](/docs/guides/second-factor/) tells the next step.
- The sign-in has four [limits](/docs/reference/limits/): `password:ip:<ip>` 20 per 15 minutes, and 10 per 15 minutes for each of `password:email:<email>`, `password:username:<username>`, and `password:phone:<phone>`.
- A sign-in by username or phone to an account in a domain that needs SSO answers [`sso_required`](/docs/reference/errors/#sso_required) after a right password. A sign-in by address answers it before the password check.
- With `password.requireVerified` on, a right password of an unverified address answers [`email_unverified`](/docs/reference/errors/#email_unverified), and a new link goes out. The [limit](/docs/reference/limits/) `password-resend:email:<email>` allows 3 links per 15 minutes. A wrong password still answers `invalid_credentials`.
- With `signUp: "invited"`, the sign-in does the same check, so a person who signs up at an invited address signs in only after the link.
- Each sign-up answer holds the sign-up proof `signUpProof`, and sets it as the HttpOnly cookie `__Host-tempo_signup`. The verify link keeps the password only in a browser with that cookie.
- A link opened anywhere else is a claim: the password goes, and the link lands on `/?password=set`. [The confirm of a sign-up](/docs/concepts/claim-rule/#the-confirm-of-a-sign-up) tells why.
- A native app whose link opens in the system browser loses the password at the confirm. Use `password.verifyBy: "code"`, and send `signUpProof` with the code.
- A native app that posts the link token itself keeps no session and no password. The link form reads the proof from the cookie only, and its answer holds no token. That is the safe side, but the person must prove the address again.
- An app on another site than the auth origin uses the code form too, and sends `signUpProof` with the code. Its proof cookie is a third-party cookie, and many browsers drop it. Then the link is a claim, and the password goes.
- Such an app also sends `signUpProof` in the body of a sign-in and of a resend before the confirm. Then the new link or code keeps the proof.
- By default every sign-up answers `{ sent: true, signUpProof }` and sets no session cookie, so the answer does not tell which addresses have an account. A new address gets the verify link. A known address gets a mail that says it has an account (`password.existingAccountMail`). The [limit](/docs/reference/limits/) `password-sign-up:email:<email>` allows 5 sign-ups per hour.
- With `password.verifyBy: "code"`, the sign-up mails a code in place of the link. See [Prove the address by a code](/docs/guides/verify-by-code/).
- With `password.uniformSignUp: false`, a sign-up opens a session, and a known address answers `email_taken`. With `password.requireVerified` on too, or with `signUp: "invited"`, a sign-up answers `{ user, verifyRequired: true }` and sets no session cookie.
- A first password needs a [fresh session](/docs/concepts/fresh-sessions/). A change while the second factor is on needs one too. A stale one answers `session_not_fresh`.
- A change with no second factor needs no fresh session, because the current password is the proof.
- [Limits](/docs/reference/limits/) lists the other limits of the password routes.

## If it fails

- [`invalid_body`](/docs/reference/errors/#invalid_body): a field is missing or has the wrong type.
- [`password_policy`](/docs/reference/errors/#password_policy): the password is too short, too long, holds a control character, or equals the address.
- [`password_breached`](/docs/reference/errors/#password_breached): `breachCheck` answered true. Ask for another password.
- [`breach_check_unavailable`](/docs/reference/errors/#breach_check_unavailable): the breach check gave no answer. Try again in a few minutes.
- [`sign_up_closed`](/docs/reference/errors/#sign_up_closed): `signUp` is `false`. With `password.uniformSignUp: false`, an address with no invitation under `signUp: "invited"` gets it too.
- [`email_taken`](/docs/reference/errors/#email_taken): only with `password.uniformSignUp: false`. A verified account or a password account has the address. Offer the sign-in.
- [`email_taken_unverified`](/docs/reference/errors/#email_taken_unverified): only with `password.uniformSignUp: false`. An unverified account has the address. Offer the sign-in.
- [`invalid_credentials`](/docs/reference/errors/#invalid_credentials): the address or the password is wrong.
- [`email_unverified`](/docs/reference/errors/#email_unverified): a change needs a verified address. With `password.requireVerified` on or with `signUp: "invited"`, a sign-in needs one too. Ask the person to open the new link.
- [`invalid_token`](/docs/reference/errors/#invalid_token) and [`token_expired`](/docs/reference/errors/#token_expired): the verify link or the reset link is spent or old.
- [`rate_limited`](/docs/reference/errors/#rate_limited): a limit of the flow is full. Wait 15 minutes.
- [`session_not_fresh`](/docs/reference/errors/#session_not_fresh): the session is older than the fresh window. Re-authenticate, then send it again.
