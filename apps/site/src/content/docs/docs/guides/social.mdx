**For:** an app developer who wants a "Continue with Google" button and a "Continue with Apple" button.

**What it does:** core runs the authorization code flow with PKCE, a state value, and a nonce, and checks the ID token of the provider.

## Before you start

- A working setup from a [getting started tutorial](/docs/start/).
- A Google OAuth client, with its client id and secret. [Social](/docs/reference/config/#social) lists the keys that hold them.
- An Apple Services ID, a Sign in with Apple key, its key id, and your team id. [Social](/docs/reference/config/#social) lists the keys that hold them.

## Steps

1. At Google, register the redirect URI `https://api.example.com/auth/social/google/callback`.
2. At Apple, register the return URL `https://api.example.com/auth/social/apple/callback`.
3. Put the secrets in your secret store, and read them into `social.google` and `social.apple`.

4. Link each button to `/auth/social/google/start?next=/home` or `/auth/social/apple/start?next=/home` on the API.
5. Core's own sign-in page shows the buttons of every configured provider. A custom page must show them too.

6. For Google One Tap or the native Apple sheet, ask `POST /auth/social/<provider>/id-token/nonce` for a nonce. Give `providerNonce` to the provider, and post the ID token with the raw `nonce` to `POST /auth/social/<provider>/id-token`. [Sign in with Google One Tap](/docs/guides/one-tap/) and [Sign in with the native Apple sheet](/docs/guides/native-apple/) give the steps.

## How it behaves

- A binding cookie of 10 minutes ties the callback to the browser that started the flow.
- Apple posts its callback across sites, so the binding cookie is `SameSite=None` and lives on the path `/auth/social`.
- Core signs a new Apple client secret of five minutes for each token exchange. Rotate the key in the Apple portal, then change `privateKey`.
- Core links a social identity to an existing user only when the provider reports the address as verified and it equals the user's address.
- An address that a verified provider proves claims an unverified account. [The claim rule](/docs/concepts/claim-rule/) tells what core deletes.
- Apple sends the name on the first sign-in only. Core stores it then.
- The start has one [limit](/docs/reference/limits/) for every provider: `social-start:ip:<ip>` 30 per 15 minutes.
- Apple's callback form post has its own limit, `social-callback:ip:<ip>` 30 per 15 minutes. Core counts a post before it reads the form.
- A user with the second factor on goes to the challenge page, with no cookie. [Turn on the second factor](/docs/guides/second-factor/) tells the next step.

## If it fails

A failure sends the browser to `appURL` with `?auth_error=<code>`:

- [`oauth_denied`](/docs/reference/errors/#oauth_denied): the person refused, or the provider sent an error.
- [`oauth_failed`](/docs/reference/errors/#oauth_failed): the code exchange or the ID token failed. Check the client secret and the redirect URI.
- [`email_required`](/docs/reference/errors/#email_required): the profile has no address.
- [`email_taken_unverified`](/docs/reference/errors/#email_taken_unverified): an unverified account has the address, and the provider did not prove it.
- [`invalid_token`](/docs/reference/errors/#invalid_token): the state or the binding cookie is missing. A second start in another tab replaces the cookie.
- [`token_expired`](/docs/reference/errors/#token_expired): the flow took more than 10 minutes. Start again.
- [`rate_limited`](/docs/reference/errors/#rate_limited): too many starts from the IP.
