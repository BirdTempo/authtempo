**For:** an app developer who must write a row of the app, refuse a write, or audit an event at a core flow.

**What it does:** core calls your function at a named point of a flow. A before hook can refuse the flow. An after hook runs after the commit.

## Before you start

- A working setup from a [getting started tutorial](/docs/start/).
- `organizations` in the config for an organization hook. [Organizations](/docs/reference/config/#organizations) lists its keys.

## Steps

1. Pass plain objects of functions in `hooks.organization`, `hooks.session`, `hooks.user`, `hooks.identity`, and `hooks.operator`.
2. To refuse, throw `hookRefusal(message)` in a before hook. The caller gets `hook_refused` with your message.
3. To write the app's own row with each core row, write it in the before hook.
   - The app's row takes the id that core minted, so the two rows match.
4. To store no IP or user agent, answer `{ ip: null, userAgent: null }` from `session.beforeCreate`.
5. For an audit trail, write from the after hooks.

## The hook points

| Group | Points |
| --- | --- |
| `hooks.organization` | `beforeCreate`, `afterCreate`, `beforeUpdate`, `afterUpdate`, `beforeDelete`, `afterDelete`, `beforeAddMember`, `afterAddMember`, `beforeUpdateMemberRole`, `afterUpdateMemberRole`, `beforeRemoveMember`, `afterRemoveMember`, `beforeInvite`, `afterInvite`, `afterAcceptInvitation`, `afterDeclineInvitation`, `afterRevokeInvitation` |
| `hooks.session` | `beforeCreate`, `afterCreate`, `afterEnd` |
| `hooks.user` | `beforeCreate`, `afterCreate`, `beforeUpdate`, `afterUpdate`, `beforeDelete`, `afterDelete`, `beforeVerify`, `afterVerify` |
| `hooks.identity` | `beforeLink`, `afterLink`, `beforeUnlink`, `afterUnlink` |
| `hooks.operator` | `beforeAction`, `afterAction` |
| `via` of a member | `create`, `add`, `invitation`, `operator`; for a removal `remove`, `leave`, or `operator` |
| `via` of a session | `password`, `magic_link`, `social`, `passkey`, `handoff`, `email_otp`, `impersonation` |
| `via` of a user create | the `via` of the sign-in, `password_reset` for a reset that creates the user, or `operator` for `createAdmin` |
| `via` of a user update | `profile`, `email_change`, `ban`, `unban` |
| `via` of a user verify | `password_verify`, `magic_link`, `email_otp`, `social`, `password_reset` |
| `via` of an identity link | `sign_in` for a social sign-in, `link` for the link of a signed-in user |
| `reason` of `afterEnd` | `sign_out`, `password_reset`, `password_change`, `claim`, `expired`, `two_factor`, `revoked`, `email_change`, `account_deleted`, `oidc_logout`, `banned`, `operator`, `impersonation_end` |

## How it behaves

- A before hook runs inside the flow's transaction, after the rank checks and the limits, and before the first write. A throw leaves no row.
- An after hook runs after the commit, before the answer. A throw cannot undo the row: core logs one line and answers success.
- Each hook gets a copy of its event. Only two hooks may change a row. `session.beforeCreate` may change `ip`, `userAgent`, and `activeOrganizationId`. `user.beforeCreate` may change `name` and `image`.
- Answer a plain object. Core reads its own enumerable fields only. A class instance or another object that is not plain answers `hook_failed`.
- In one sign-in that creates a user, the order is `user.beforeCreate`, `identity.beforeLink`, and `session.beforeCreate`, all before the first write. After the commit, the order is `user.afterCreate`, `identity.afterLink`, and `session.afterCreate`.
- A flow that moves an existing user from `emailVerified: false` to true runs `user.beforeVerify` and `user.afterVerify` once. They take the place of `user.beforeCreate` and `user.afterCreate` in that order.
- `user.beforeVerify` sees the stored row, still unverified. A refusal leaves the user unverified. The magic link, the email code, the verify link, and social spend their proof first, so a refusal spends it. The reset keeps its link.
- Two proofs of one user at once both run `user.beforeVerify`. One claims the user and runs `user.afterVerify`. The other finds the user verified. The magic link, the email code, social, and the reset sign in that user. The verify link opens no session. It answers `invalid_token` when the claim deleted the user's password. So a before can have no after.
- A user that a flow creates verified fires the create points, not the verify points. The change of address fires the update points.
- The sign-up rule runs before `user.beforeCreate`. So no user hook sees a create that `signUp` refuses.
- A claim fires the verify points only. The `email` identity, the social fill of the name and the image, the sweep, and the importer fire no user or identity hook.
- `user.beforeUpdate` can run more than once for one change, with `via: "profile"` and with `via: "email_change"`.
- A parallel write that lands first makes core read the user row again. Then `user.beforeUpdate` runs again on the new row. Write the hook so that a second call does no harm.
- `identity.beforeLink` with `via: "link"` runs inside the transaction of the link, before the identity write.
- It can run twice for one identity, when two link states of one user race. The second write then fails.
- `identity.beforeUnlink` runs inside the transaction, after core counts the ways in and locks the user row, and before the first delete. It has no `via`.
- An unlink that `last_credential` refuses runs no hook. `identity.afterUnlink` runs after the commit.
- The account delete runs `organization.beforeDelete` for each organization that goes, then `user.beforeDelete` with the ids of those organizations. Both run inside the transaction, before the first delete.
- After the commit of the delete, `session.afterEnd` fires once per session with `account_deleted`. Then `organization.afterDelete` and `user.afterDelete` fire.
- The rows that the delete removes fire no member or identity hook.
- A refusal message of 1 to 200 characters with no control character reaches the caller. Any other message becomes "The app refused this request.".
- Hooks have no timeout. A hook that never settles holds the request, and a before hook holds the transaction.
- The sweep fires one hook only: `session.afterEnd` with `banned` or `operator` for a session that a ban or a revoke left for it. `expired` fires only when a request presents a token after its expiry.
- Core has no request hooks. Wrap `auth.handle`, and read `auth.caller(request)`.

:::caution
Warning: on Postgres with a pool of one connection, a before hook that queries the same client stops the request until the pool times out. Use a second connection for the app's own write.
:::

## The operator points

- `hooks.operator` needs `operator.users`. [Run the operator tools](/docs/guides/operator-tools/) turns the tools on.
- `beforeAction` gets the audit row of the act, with no id yet. It runs before the act's transaction, so before its first write. A refusal answers `hook_refused`, and the act writes nothing.
- `afterAction` gets each stored audit row once, after the commit. A throw writes one log line, and the act stays. Send the row to a separate system here.
- `afterAction` also gets each `impersonation_stop` row that another flow writes, such as the user's end of an impersonation session. No `beforeAction` runs for such a row.
- In the six member points, `by` is null for an act of an operator secret or of the app. Those acts have no user.
- `via: "operator"` of a member is the grant or the revoke of the platform role, or `createAdmin`.
- `banned`: a ban, or a session of a banned user that a request or the sweep ends. `operator`: an operator ends the sessions, or revokes the platform role. `impersonation_end`: the stop of an impersonation.
- `user.beforeUpdate` with `via: "ban"` can run more than once for one ban, when a parallel write lands first.

## If it fails

- [`hook_refused`](/docs/reference/errors/#hook_refused): a before hook threw `hookRefusal(message)`. The body carries `message`.
- [`hook_failed`](/docs/reference/errors/#hook_failed): a before hook threw another error, or a session patch or a user patch was wrong.
- [`not_found`](/docs/reference/errors/#not_found): a session patch named an organization that the user is not a member of.

`createAuth` refuses a hook that is not a function and a name that is no hook point. It also refuses a group that core does not have, and organization hooks while `organizations` is off.
