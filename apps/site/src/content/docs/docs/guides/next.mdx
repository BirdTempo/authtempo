**For:** a developer of a Next.js 16 app on the App Router.

**What it does:** the app serves the routes of authtempo under `/auth`, and reads the session in a server component. A person with no session goes to the sign-in page.

## Before you start

- Node 22.18 or newer.
- A storage adapter for production. [Getting started](/docs/start/) shows D1 and Postgres.

## Steps

1. Add the packages: `pnpm --filter my-app add @authtempo/core @authtempo/next`.
2. Make the auth instance in a function, so `next build` reads no secret.
3. Mount the routes in `app/auth/[...path]/route.ts`.
4. Read the session with `authSession` in a server component.
5. Protect paths with `authProxy` in `proxy.ts`.
6. Set `BASE_URL` and `AUTH_SECRET` in the environment of the server.
7. Read `GET /auth/session` from the browser, so the browser gets the renewed cookie.
   - The page below is a server component, and it makes no such read. Add one when you copy it.
   - The session store of `@authtempo/react` makes the read. A `fetch("/auth/session")` in a client component makes it too.

## How it behaves

- A server component cannot set a cookie, so `authSession` leaves the sliding refresh for the browser. Only the browser's read of `GET /auth/session` sends the renewed cookie.
- An app with no such read loses the cookie at its first `Max-Age`, and the person must sign in again.
- Without `auth`, the proxy checks only that a session cookie is present, or a bearer that starts with `ts_`. The page checks the session. Never trust the proxy alone.
- The session cookie is `__Host-tempo_session` by default. Set `cookieName` on the proxy when the config of core sets another name.
- Next 16 renamed middleware to proxy. A file named `middleware.ts` gets a deprecation warning from Next.

## If it fails

- [`origin_not_trusted`](/docs/reference/errors/#origin_not_trusted): the page posts from an origin that is not `BASE_URL`.
- [`unauthorized`](/docs/reference/errors/#unauthorized): no session. The proxy sends the person to the sign-in page.
