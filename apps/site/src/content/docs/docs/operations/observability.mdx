**For:** an operator who watches an API with authtempo in production.

**What it does:** this guide sends the events of core to a sink, reads the trace of one request, and sets the alerts. It also lists each default line.

## Before you start

- An API that runs. [Deploy](/docs/operations/deploy/) puts it on Workers, on Node, or on Bun.
- The event list. [Events](/docs/reference/events/) gives the level and the fields of each event.

## Pick a sink

With no `observe` config, core writes each default line with `console`, and nothing leaves the app. With a sink, core writes no `console` line, and the sink gets each event, with one exception. Core writes `secret.low_entropy` with `console` while `createAuth` reads the config, and no sink gets it. A sink has one call, `write(batch)`. The package `@authtempo/observe` has three sinks:

| Sink | Where the events go | Use it for |
| --- | --- | --- |
| `workersLogsSink` | One `console` call of one object for each event, in Workers Logs | The default on Workers. Each field is indexed. |
| `analyticsEngineSink` | One data point for each event of a chosen list | Counts over time, read with SQL. |
| `otlpSink` | OTLP logs, traces, and metrics over HTTP | A collector of the app, off Workers too. |

An app can write its own sink. It gets the events after the answer, and it owns what it does with them.

## The trace of a request

Each answer of `handle` carries the header `x-authtempo-trace`, with the trace id of the request. Each event of that request holds the same `traceId`. A browser on a trusted origin can read the header, because core exposes it there.

1. Ask the person for the value of `x-authtempo-trace`, or read it from the network panel.
2. Search the sink for that `traceId`. The `request` event names the route, the status, the outcome, and the code.

Core makes a new trace id for each request. With `observe.trustTraceparent: true`, a valid W3C `traceparent` header gives the trace id and the parent span id. An invalid or all-zero header is ignored. A client trace id is off by default, because a client could join its requests to the trace of another person.

## What an event can hold of an address

By default an event holds no IP, no user agent, and no email. `observe.include` turns each one on:

| Key | Values | What the event holds |
| --- | --- | --- |
| `ip` | `"none"`, `"hash"`, `"raw"` | `ipHash`, a keyed hash of 32 hex, or `ip`, the address of `clientIp` |
| `userAgent` | `"none"`, `"raw"` | `userAgent`, at most 256 characters with no control character |
| `email` | `"none"`, `"hash"` | `emailHash`, a keyed hash of 32 hex. An event never holds a raw email. |

The keyed hash is HMAC-SHA256 under a key that HKDF derives from the current app secret. A rotation of the secret changes every hash, so a hash from before the rotation does not join a hash after it.

## How it behaves

- `emit` is synchronous, and no flow waits for a sink. The buffer holds `observe.buffer` events, 1000 by default. A push into a full buffer drops the event and counts it.
- The flush runs after the answer. It calls `write` once, and waits for it for at most `observe.flushTimeoutMs`, 2000 ms by default.
- A lost batch counts as `sink_timeout` or `sink_threw`. The next batch starts with one `observe.dropped` event that holds the counts. `auth.observe.stats()` answers the same counts in process.
- Core cannot stop a sink that loops on the CPU in a synchronous `write`. Such a sink holds the isolate, so keep `write` short.
- On Workers, the `waitUntil` work of one request has 30 seconds after the answer in all. Each `waitUntil` of that request shares the time.
- Core replaces each secret value of the config with `***` in each string field of an event, before the buffer, with or without a sink. Each sink of `@authtempo/observe` scrubs again with its own `secrets` list.
- The `method` field of the `request` event holds the method token of the request, `HEAD` too.
- A redirect counts as a failure only when core marked it with an error code. A `next` value of a client that holds `auth_error` gives no failure.
- `analyticsEngineSink` writes at most 200 data points in one flush, `AE_MAX_POINTS`. Analytics Engine takes at most 250 for each Worker invocation (Cloudflare limit, read 2026-10-21). The 50 others stay for the points of the app.
- Over 200 chosen events in one batch, the sink writes the first 200 and throws. Core then counts each event of the batch in `sink_threw`.
- Each OTLP post aborts after `timeoutMs`. Each OTLP sink makes a random `service.instance.id` at its first write, so each isolate writes its own metric stream.
- An event is telemetry, and it can drop. The audit table of the operator tools is the record of an operator act.

## The health and readiness probes

`GET /auth/health` answers 200 `{ "status": "ok" }` in every deployment, and reads no storage. `GET /auth/ready` exists only with `observe.readiness: true`. It checks the store, and answers 200 `{ "status": "ready" }` or 503 [`not_ready`](/docs/reference/errors/#not_ready). One result holds for 10 seconds. [Deploy](/docs/operations/deploy/) gives a probe for each host.

## The default lines

With no sink, core writes each line of this table with `console`, with the text and the arguments of each release before. With a sink, core writes only the `secret.low_entropy` line, while `createAuth` reads the config. No sink gets that event. A line holds an event name, a provider name, a row id, an HTTP status, or an error name. It never holds a token, a code, a cookie, an address, or an error message. The [Events](/docs/reference/events/) page lists the fields of each event. A site check holds this table to the code.

## If it fails

- No event in a day of traffic: `handle` gets no `waitUntil`, or `observability.enabled` is `false`. On Node and Bun, the flush timer does not run.
- `observe.dropped` with `buffer_full` above 0: the buffer filled before a flush. Raise `observe.buffer`, or on Node and Bun flush more often.
- `sink_threw` counts with `analyticsEngineSink`: one batch held more than 200 chosen events. Give the sink a shorter `events` list. A larger `observe.buffer` makes the batch larger, not smaller.
- `sink_timeout` counts: the collector does not answer in `observe.flushTimeoutMs`.
- Many `authtempo: unhandled error` lines with a storage error: a migration is missing. [Upgrades](/docs/operations/upgrades/) tells how to apply it.
- [`hook_failed`](/docs/reference/errors/#hook_failed) answers: read the `authtempo: before hook failed` line of the same time.
